# Formation work - contracts between the parts (coordinator: «Маршрутизатор моделей», user decision 2026-10-25)

Design source: `docs/design/FORMATION_SECTORS.md` (+ `formation-sectors.html`). This file fixes the DATA the parts exchange, so
the TypeScript simulator (Training Ground), the C++ rules and the Unreal map generator can be built in parallel and meet.
Units: centimetres, degrees, seconds. Yaw: strictly UE - X forward, Y right, yaw = atan2(dy, dx) in degrees, growing from +X
towards +Y (clockwise seen from above); "clock" sectors are relative to the leader's heading: clock c -> yaw = heading + 30*c
(12 = heading, 3 = right = heading + 90, 9 = left = heading - 90). Coordinator decision 2026-10-25 (the first version had the
sign mirrored). Config: `Content/Data/FormationLab/formation_config.json`, schema `codex.formation_config/1`,
`params: { "<key>": { value, min, max, unit, doc } }`, scalars only; angles relative to the leader's heading (or the wall's
outward normal for `wall.*`), positive = right. Owned by the cloud session (Training Ground); the tuner changes only `value`.

## 1. Layout JSON - `Content/Data/FormationLab/<name>.json` (one file feeds the simulator AND the Unreal map generator)
```json
{
  "schema": "codex.formation_layout/1",
  "name": "formation_lab_01",
  "bounds": { "min": [-6000, -6000], "max": [6000, 6000] },
  "ground_z": 0,
  "spawn": { "pos": [0, 0], "yaw": 0 },
  "walls": [ { "id": "W1", "a": [x, y], "b": [x, y], "height": 300, "thickness": 40 } ],
  "zones": [ { "id": "Z1", "kind": "open|corridor|wall_run|gap_run|corner|wall_end", "poly": [[x, y], ...] } ],
  "routes": [ { "id": "R1", "pace": "walk|run", "points": [[x, y], ...],
               "expect": [ { "zone": "Z1", "formation": "diamond|wedge|column|line|echelon_left|echelon_right|wall|hedgehog|blizzard" } ] } ]
}
```
- Walls are straight segments; a gap = two segments. Corners = two segments sharing an end point.
- Zones are labels for the checks (what the terrain classifier SHOULD say), not geometry.
- Routes are the leader's click path; the bot walks the squad along each route.
- Optional `"props": [ { "id": "HEAT_A", "kind": "heat_source", "pos": [x, y] } ]` - set dressing for the map builder only
  (heat_source -> an unlit ACampfireActor for the hedgehog); the rules and the checks ignore it (cloud session, stage 5).
- v2.1 optional per route: `"threats": [ { "pos": [x, y], "since_s": 0 } ]` (a threat the squad knows from sim time since_s on:
  an enemy seen, or heard / last known position; it counts while younger than `bypass.threat_memory_s`) and
  `"expect_bypass": [ { "wall": "W_G_19", "wall_on": "left|right" } ]` (bot check 8: the side the squad must pass that wall on -
  the wall on its left / right as it goes by). A route with expect_bypass crosses its wall on purpose (the audit does not warn).
- The big lab `formation_lab_01.json` is generated by `npm run lab:gen` (Tools/TrainingGround/src/movement/cli/genLab.ts) -
  edit the generator, not the JSON; `Scripts/Editor/build_formation_lab.py` builds `/Game/Maps/L_FormationLab` from it
  (TargetPoints `<route id>_<n>`, tags FormationLabRoute + the route id; v2.1 threats: TargetPoints `<route id>_threat_<n>`, tags
  FormationLabThreat + the route id + `since_s=<s>`).

## 4. Movement bot report - `Saved/TrainingGround/movement/report.md` (<= 30 lines; the ONLY thing a coding agent reads)
Header: layout, routes, runs, seed. Then one line per check with pass / fail counts and the worst case (route id, time):
1. wall stare: nobody looks into a wall closer than 200 cm (facing within 45 deg of the wall normal, towards it);
2. rear cover: with 3+ members (v2.2: the triad too) the 5-7 o'clock sector is watched >= 90 % of patrol time;
3. flicker: formation changes per 100 m of route (target <= 1 outside expected changes);
4. expected formation per zone (routes[].expect) matched;
5. slots: no slot inside a wall / off the walkable area; spacing within config;
6. pace: the man at the rear PLACE keeps <= 150 cm behind his slot at patrol pace (3+ members since v2.2; p95; not while the wall layout is in effect -
   its slots are destinations at the wall, not a following formation);
7. (v2.1) squad split: no wall between the leader and a member's slot or position, nor between chain neighbours
   (`FormationGuardRules::ChainPairs`), for >= 0.3 s; in the trail column (guard level 2) the chain of neighbours (slots and
   positions) is judged instead of the leader's straight line (the column wraps a wall end on his own path);
8. (v2.1) bypass side: each `expect_bypass` wall passed on the expected side (the leader's real trajectory, `wallSideOf`);
9. (v2.1) corner: when the leader passes a free wall end beside him on patrol, some member's cone holds the corner or the
   area behind it (fov / 2 - 10 deg);
10, 11. info: rear cover with 3 men; stuck followers / slot fallbacks.
Checks 3 and 4 judge the REQUESTED formation (`Frame.requested`: the terrain's / the menu's decision); the guard's fallbacks are
geometry, covered by 7. `npm run bot:movement -- --manual <item>|all`: every run with that menu choice; `all` = auto + every
item, the report is a matrix of failing runs per check (`manual_matrix.md`); a manual formation is gated by 1, 5 and 7 (it
ignores the terrain on purpose, but since v2.1.1 nobody looks into a wall in it either).
Raw runs: `Saved/TrainingGround/movement/runs.jsonl` (never read by agents). Advice (optional): Jev (`TYPESAFE_API_KEY`) or the
Claude API (`ANTHROPIC_API_KEY`) turns runs.jsonl into <= 10 lines of tuning advice appended to the report; without a key the
report says "no model advice".

## 6. Bot training on the user's API tokens (user request 2026-10-25: "use the API tokens as much as possible, train the bot through the cloud APIs")
The tuner loop - `Tools/TrainingGround` department "movement", `npm run train -- --budget-usd <N> --rounds <N>`:
1. simulate a series (deterministic TS, 0 tokens): every route x N seeds with the current `formation_config.json`;
2. distil the series to a compact JSON summary (check stats, worst cases, current parameters) - never raw runs;
3. ask the Claude API (`ANTHROPIC_API_KEY`, model `claude-opus-5-5` for proposals, `claude-sonnet-5-5` for summaries; Jev
   `TYPESAFE_API_KEY` for typed pass/fail judgments when available) for the next parameter set as strict JSON within allowed
   ranges (the ranges live next to the defaults in formation_config.json);
4. keep the best set (score = weighted checks of section 4), stop on budget, on no improvement for K rounds, or on all checks green;
5. write `Saved/TrainingGround/movement/train_report.md` (<= 30 lines: rounds, spend, best score, the winning parameters as a
   diff) and `train_best_config.json`. A coding agent reads only train_report.md; the winning config goes into main only after
   the coordinator's review.
Budget: a hard cap per run (`--budget-usd`, default 5), the spend counted from the API's token usage and logged per call; the
key is read from the environment / HKCU and never printed. The same loop pattern later serves the waves bot and the
level-design bot (Training Ground departments).
Where it runs: the user's PC (the key lives there). The cloud session builds the loop with a mock client (no key, no network)
and a `--dry-run`; the coordinator's local agent wires the real client and runs the first training.

## 7. Integration requirements for the runtime (stage 6; found by the simulator, coordinator 2026-10-25)
- **Follower speed with velocity lead.** Today `SquadFormation::ComputeFollowerSpeed` slows a follower proportionally inside
  `SlowRadius` (250 cm) even while his slot moves, so at walking pace every follower trails ~2 m behind his slot and the rear
  man never closes a gap (the sectors / pace in the game then differ from the simulator). The runtime must move a follower
  with the slot's own velocity (feed-forward) plus a proportional correction towards the slot: `v = v_slot * jitter +
  dir * min(top * catchup_mult, d * FOLLOW_GAIN)`, `FOLLOW_GAIN = 2 / s`, capped by `top * move.catchup_mult` and, walking
  backwards (> 120 deg off his facing), by `pace.walk_speed * move.backward_mult`; stop only when within 25 cm AND the slot is
  still. v2.1.1: when the sum exceeds the cap, keep the slot's velocity (the formation's own speed) and shorten only the
  correction: `v = v_ff + dir * min(want, -(v_ff . dir) + sqrt((v_ff . dir)^2 - |v_ff|^2 + cap^2))` (if |v_ff| >= cap: v_ff scaled
  to cap) - scaling the whole sum let a big sideways correction (a fold, a swing) steal forward speed and the man fell behind
  his slot (sample_small's pace failure). Reference: `Tools/TrainingGround/src/movement/sim.ts` `stepTowards`.
- **Walking into the wall layout:** a member walking to his wall slot faces his travel direction and turns to the layout yaw
  only within 100 cm of the slot (else he looks into the passage walls on the way; sim `WALL_TURN_DIST`).
- **v2.1: fallback slots on the leader's side.** `SquadFormation::ComputeFallbackSlots` (a slot inside a wall turned round the
  leader in 30 deg steps) must also reject a candidate whose straight line from the leader crosses a wall - a walkable point
  behind a wall splits the squad (found by check 7: a manual wedge's left slot 20 cm off a wall fell back to the far side).
- **The wall layout only on arrival.** A wall straight ahead (`at_wall`) while the leader still walks is a corner to turn: keep
  the previous formation; switch to `FormationWallRules::Layout` when the leader stops at the wall (or on a cover order).

## 8. v2 - the path hold (implemented 2026-10-25, coordinator; was "planned" here)
- `classify.hold_time` (s) is replaced by **`classify.hold_distance`** (cm of the leader's path, default 500 >= the column length,
  range 150-1200). Pace-independent (a hold in seconds shrank in distance at a slow patrol pace and short gaps flipped again).
- **Asymmetric**: a TIGHTER raw class (rank open 0 < wall_left / wall_right 1 < corridor 2 < at_wall 3) takes over at once -
  the squad never walks a diamond into a passage; a LOOSER (or equal-rank) one only after it has been the raw class for
  hold_distance of the leader's path (standing still adds nothing). Leaving at_wall (a new move) is immediate.
- `Classify(walls, leaderPos, leaderYaw, destination, state, stepDistance, config) -> state`, pure:
  `state = { current, candidate, candidateDistance, passageWidth }` (start `{null, null, 0, null}`); `stepDistance` = the leader's
  path this tick. `passageWidth` = PassageWidth while `current` is corridor, HELD with the class after the leader left the
  passage (the column's tail keeps the narrow sectors) - this is what LookYaw takes. Golden: Classify cases are state in /

## 14. v2.4 - the wall end (user bug report 2026-10-26; FORMATION_SECTORS.md "v2.4")

### 14.1 `FormationWallRules::OpenArcCoverage(walls, positions, lookYaws, fov, probe) -> { open, covered, pct }`
The probe ring: `360 / WALL_END_STEP` (2 deg) points at `probe` cm round the members' mean position, the first at yaw -180. A point is
open when some member's straight line to it keeps `WALL_END_RAY_RADIUS` (1 cm) from every wall body (`segmentBlocked`; so a zero-thickness
traced face blocks too); covered when some member with such a line has its direction within fov / 2 (+1e-9) of his look. pct = 100 x
covered / open (100 when nothing is open). TS `openArcCoverage` (members `{pos, yaw}`).

### 14.2 `FormationWallRules::EndLooks(walls, slots, config, fixed = []) -> { spread, basePct, pct, slots }`

decided (merge with formation/v24-corner-peek: the corner stack's point man and trailing end). basePct = OpenArcCoverage of the slots with their
looks (`wall_end.probe_dist`, `sight.fov`). Fewer than 3 slots, or basePct >= `wall_end.cover_pct` - 1e-9 -> unchanged (spread false;
every face layout, the pair). Else: K and every `fixed` role keep their looks; `held` = the open points their cones hold (from their slots,
slot order); then, while the others are left:
for every remaining member (slot order) and every look y = -179..180 (whole degrees) not within look.wall_angle (- 1e-6) of the direction
to the closest point of a wall whose surface is within look.wall_dist of his slot (and not 1e-6 from it), gain = the open points he sees,
not held, inside +-fov / 2 of y; his best = the largest gain, ties the smallest |y - his layout look|, then the first (lower) y; the member
with the largest best gain wins (ties: the earlier member); a best gain of 0 ends the loop (the rest keep their layout looks); the winner
takes y, his points become held. pct = OpenArcCoverage of the result; pct <= basePct + 1e-9 -> unchanged (spread false). Positions and order
never change. Keys `wall_end.probe_dist` 600 (200-1500 cm), `wall_end.cover_pct` 95 (80-100 %); config 78 keys.

## 17. The custom formation (game designer decisions 2026-11-01; FORMATION_SECTORS.md "Custom formation")
The player places the squad's shape himself (hold-B menu -> Custom 1 / 2 / 3 -> the placement mode) and the squad keeps it like any
other formation: slots in the leader's frame, rotating with the heading; the looks are the player's, fixed relative to the heading.
TS `Tools/TrainingGround/src/movement/custom.ts` (`FormationCustomRules`), C++ `Source/CodexTactics/*/Formation/FormationCustomRules.*`,
golden `formation_Custom*.json`. Constants (same in TS and C++, not tuned): `CUSTOM_MAX_RADIUS` 4000 cm (was 1000 until 2026-11-01: the game designer, bug_05 - the 10 m
reach "ruins everything"; 4000 is only a sanity reach against a mis-click on the far horizon), `CUSTOM_DRAG_MIN` 50 cm,
`CUSTOM_SLOT_COUNT` 3, `CUSTOM_MAX_MEMBERS` 4.

### 17.1 The slot storage (`FFormationCustomShape`; save game / campaign carry / golden)
```json
{ "members": [ { "squad": 0, "fwd": 0, "right": 0, "look": 0 },
               { "squad": 2, "fwd": -250, "right": 300, "look": 60 } ] }
```
- `members[0]` = the ANCHOR: the operative who led when the shape was confirmed; `fwd` / `right` = 0, `look` = 0 (his look is the
  shape's heading). The others follow sorted by `squad` ascending. Up to 4 entries, `squad` (the operative's `SquadIndex`) unique.
- `fwd` / `right`: the member's place in the anchor's frame, cm (forward along the heading, right = heading + 90); `look`: his look
  relative to the heading, deg in (-180, 180]. Stored rounded to 0.1 cm / 0.1 deg (`RoundShape`, round half away from zero).
- An empty slot = no members (`null` in JSON). Three slots per squad (`custom_1..3`). Save game: `game_state.formation_custom` =
  `[shape | null, shape | null, shape | null]` + `game_state.formation_menu_choice` (`auto` or a menu item id); the campaign carry
  (`FCampaignSquadCarry`) the same two.

### 17.2 `CustomSlots(shape, present, leaderPos, leaderYaw, config) -> [{ squad, role, pos, yaw, fixed }]`
`present` = the squad indices of the living members in the formation, the LEADER first, then the followers in squad order.
- Places: place j = `shape.members[j]` (place 0 = the anchor at 0, 0, look 0). Who stands where: the leader -> place 0. The operative
  stored at place 0 (when present and not the leader) -> the place the leader had in the shape (when the leader is in the shape; else
  he is an extra). Everybody else present -> his own stored place. A present member the shape lacks -> an extra. A stored member not
  present (dead, missing) is skipped; the others keep their places.
- Output order: the leader first, then the others in `present` order. Roles = `rolesFor(count)` by that order (K, then P / Z, P / L / Z);
  `present` beyond CUSTOM_MAX_MEMBERS is cut (the runtime's 5th man keeps the old slot math).
- Placed: `pos = localToWorld(leaderPos, leaderYaw, [fwd, right])`, `yaw = normYaw(leaderYaw + look)`, `fixed = true`.
- Extras (in output order, k = 1, 2, ...): `pos = localToWorld(leaderPos, leaderYaw, [minFwd - k x column.spacing, 0])`, minFwd = the
  smallest `fwd` of the places given out (0 with the leader alone); `yaw = normYaw(leaderYaw + 180)`, `fixed = false`.
- An empty shape -> `[]` (the caller falls back to the terrain's formation).

### 17.3 `BlockedRoles(walls, slots, leaderPos, config) -> roles`
The roles (slot order, the leader never) whose straight line `leaderPos -> slot` passes within `guard.clearance` of a wall body
(`segmentBlocked`). No chain pairs: the custom shape has no neighbour order; every slot must see the leader.

### 17.4 `Resolve(walls, shape, present, leaderPos, leaderYaw, ahead | null, state, stepDistance, config, allInSight = true) -> GuardState`
The guard of 10.1 / 13.6 for the custom shape: `requested = 'custom'`, `effective = 'custom'` at level 0, `'column'` at level 2 (the TRAIL
column, `FormationShapeRules.TrailSlots` - the existing fold); there is no level 1 (no mirror) and no turn fold (a sharp turn alone does
not fold it: the player's shape, as Q2 = a for the manual hedgehog / blizzard / column). Raw level 2 (`cause 'wall'`) when BlockedRoles
is not empty for `CustomSlots` at the leader, or at `ahead` (`{pos, yaw}`, the guard.lookahead pose), or `allInSight` is false; else 0.
Hysteresis exactly as 10.1: `state.requested !== 'custom'` or raw >= state.level -> the raw level now; else (level 2 waiting for 0)
`walked = (state.candidate === 0 ? state.candidateDistance : 0) + max(0, stepDistance)`; walked >= `classify.hold_distance` -> level
0, else level 2 held (`candidate 0`, `candidateDistance walked`, the held cause). The caller does not call it for an empty shape.

### 17.5 `Look(walls, pos, yaw, currentYaw, config, held = null) -> yaw`
The player's fixed look is kept unless it points INTO a wall: blocked = some wall whose surface is within `look.wall_dist` of pos (and
whose closest point is >= 1e-6 from pos) has the direction to its closest point within `look.wall_angle` (strictly, - 1e-6) of yaw.
Not blocked -> `normYaw(yaw)` (no sliver / hold logic: his look stays his). Blocked -> `FormationSectorRules.ClearLook(walls, pos, yaw,
currentYaw, config, held)` (13.1 / 13.4; no limit, no ahead).

### 17.6 Placement (pure; the runtime's placement mode)
- `DragLook(ghostPos, cursorPos, defaultYaw) -> yaw`: `dist(ghostPos, cursorPos) < CUSTOM_DRAG_MIN` -> `normYaw(defaultYaw)` (a plain
  click: he looks along the squad's heading), else `yawOf(cursorPos - ghostPos)`.
- `CanPlace(ghosts [{squad, pos}], anchorSquad, squad, pos, config) -> 'ok' | 'too_far' | 'too_close'`: the ghosts after the placement
  (squad's ghost moved to pos, added when missing). `too_close` when some other ghost is within `slot.min_spacing` of pos; `too_far` when
  any ghost (pos's included) is farther than CUSTOM_MAX_RADIUS from the anchor's ghost (squad == anchorSquad: the anchor moves, the
  others must stay within reach; no anchor ghost -> no reach test). Checked in that order. CUSTOM_MAX_RADIUS is a generous sanity reach
  (40 m, 2026-11-01): the placement has no other range limit - never the tactical pause's order radius (the placement is no pause order;
  the runtime also hides the pause's 12 m ring while placing); the runtime adds only "a walkable spot" (on the nav mesh, not inside a wall).
- `ShapeFrom(ghosts [{squad, pos, yaw}], anchorSquad) -> shape`: the anchor ghost's pos / yaw is the frame; each ghost -> `fwd` / `right`
  = his pos in that frame, `look = normYaw(yaw - anchorYaw)`; the anchor first (forced 0, 0, 0), the others by squad ascending, at most
  CUSTOM_MAX_MEMBERS; `RoundShape` applied. No anchor ghost -> empty.

### 17.7 The menu (section 9 extended)
- Items `custom_1`, `custom_2`, `custom_3` (C++ `EFormationMenuItem::Custom1..3`, values 8-10; `ItemCount` stays 8 = the ring). They
  are three discs in a row BELOW the ring: centres `(dx, dy) = ((k - 1) x CUSTOM_ROW_SPACING, CUSTOM_ROW_Y)`, k = 0..2, radius
  `CUSTOM_ROW_RADIUS` (widget px: 100, 280, 40). `CustomItemAt(dx, dy) -> custom_(k+1) | null`: the first disc with hypot <= radius.
  `HitAt(dx, dy, deadZonePx) = CustomItemAt(dx, dy) ?? ItemAt(dx, dy, deadZonePx)`; `Move` uses HitAt (ItemAt is unchanged).
- `Release(state, memberCount, filled = [false, false, false], edit = false)`: on `custom_k` (enabled with >= 2 members, else
  `disabled`): `filled[k-1]` and not `edit` -> `picked` (choice = custom_k, holds until Auto); else -> effect `edit` (the choice
  unchanged; the runtime opens the placement mode for slot k). Every other case as section 9.
- `Resolve(choice, memberCount)` gains `customSlot`: `custom_k` -> `{ manualFormation: 'custom', allForward: false, customSlot: k }`
  (null for every other choice); the runtime falls back to Auto when that slot is empty. Below 2 members -> Auto as before.
- Labels (English, the widget): "Custom 1" .. "Custom 3"; an empty slot "Custom 1 (empty)"; the HUD while folded "Custom 2 -> Column (wall)".
- Golden `formation_Menu.json` gains the op `customAt` (`dx`, `dy` -> `item`), `release` cases with `filled` / `edit` and `resolve`
  cases with `customSlot` (the old cases unchanged).

### 17.9 Readings fixed by the TS reference (2026-11-01; the C++ port follows them)
- Boundaries: CanPlace `too_close` = distance < slot.min_spacing, `too_far` = distance > CUSTOM_MAX_RADIUS (4000.0 is ok); DragLook
  < CUSTOM_DRAG_MIN is a click (50.0 is a drag). RoundShape = `sign(v) x round(|v| x 10) / 10` (-0 -> 0), the look then `normYaw`
  (-179.96 -> 180). Resolve's held branch keeps `state.cause ?? 'wall'`; walked == hold_distance releases; a negative step counts 0.
- CustomSlots: members[0] is the anchor whatever its stored numbers; the leader stored but the anchor dead -> the leader takes place 0
  and his own stored place stays empty; minFwd counts the leader's place 0 (so <= 0). In the existing rules `Slots('custom')` and
  `BlockedRoles('custom')` are `[]` (the custom rules own them); `localSlot` / `relativeLook` give 0.
- Look: the wall test = surface distance <= look.wall_dist, the closest point >= 1e-6 away, |direction - yaw| < look.wall_angle - 1e-6.
- Sim: level 0 skips the corner watch and the coverage allocator (the looks are the player's) and keeps the places in squad order (no
  minimal-travel reassignment); level 2 is the trail column with its reassignment. Golden `formation_Menu.json` also has the op `hitAt`
  (`dx`, `dy`, `deadZonePx` -> `item`); its old `resolve` cases omit `customSlot` (absent = null).
- Golden counts: CustomSlots 235, CustomGuard 306, CustomLook 252, CustomPlace 197, Menu 160 -> 466. Bot `--manual custom`: checks 1 / 5 / 7
  green on sample_small (24 runs) and formation_lab_01 (168 runs).

## 18. v2.6 - the game designer's answers to the red team v2.5 questions (2026-11-01; FORMATION_SECTORS.md "v2.6", FORMATION_REDTEAM_V25.md Q1-Q3)
### 18.1 Rule: short obstacles beside the path are no side walls (Q1 = b; `rules.ts` `obstacleGroups` / `sideWalls`)
- New keys `classify.side_min_length` 150 (0-400 cm; 0 = off = v2.5.1) and `classify.side_join_gap` 50 (0-150 cm).
- `obstacleGroups(walls, gap)` / C++ `FormationTerrainRules::ObstacleGroups`: walls whose BODIES come within `gap` of each other
  (`segSegDist(a, b, a', b') - (t + t') / 2 <= gap`) are one obstacle (connected components); each wall's group = the lowest wall index in it.
- `sideWalls(walls, yaw, config)` / C++ `SideWalls`: every wall of an obstacle whose extent ALONG the heading - over its walls, the centre
  line's projections on `dirOf(yaw)` +- thickness / 2 - is `>= classify.side_min_length`; C++ also keeps a runtime probe hit
  (`FFormationWall::bProbeHit`). `rawClass` / `ClassifyRaw` and `PassageWidth` give the side probes (`sideClearance` / `SideClearance`)
  only these walls; the at_wall (ahead) rays, `SideWidth`, the guard and ClearLook are unchanged.
- Runtime: the classifier's walls are trace hits (`FormationRuntime::WallFromHit`, 20 cm, `bProbeHit = true`); a SIDE probe's hit (> 45 deg
  off the heading) is dropped when `FormationTerrainRules::IsShortSideObstacleAt(boxWalls, hit, heading, config)` - some box wall's body within
  20 cm of the hit and every such wall in an obstacle (the same join rule, a breadth-first walk from it) shorter than the key; no box wall
  there (complex collision) -> kept. Box walls = the guard's world walls (`GatherFormationWalls`), else gathered round the probe.
  `Codex.Formation.ShortSideObstacles` 0 = every hit (A/B); counter `GetFormationShortSideHits`.
- Golden: `formation_Classify.json` / `formation_PassageWidth.json` / `formation_SideWidth.json` gain the scenes `pillar_left`,
  `stub_right_120`, `short_wall_left_200`, `pieces_left`, `posts_right`, `pillar_in_corridor`, `stub_on_wall_right`.
### 18.2 Rule: the lagging rear guard turns round (Q2 = b; `FormationSectorRules.RearCatchUp` / `RearWayBlocked`)
- New keys `move.rear_turn_lag` 150 (50-400 cm) and `move.rear_turn_back` 50 (0-200 cm).
- `RearCatchUp(lag, turned, wayBlocked, config) -> turned'`: `turned ? lag > rear_turn_back : !wayBlocked && lag > rear_turn_lag`. `lag` =
  `dot(slot - pos, dirOf(heading))` (how far his slot lies ahead of him along the squad's heading; check 6's measure).
- `RearWayBlocked(pos, slot, others, config)`: some other member within `slot.min_spacing + REAR_WAY_MARGIN` (20 cm) of the segment pos ->
  slot and ahead of him (`dot(other - pos, slot - pos) > 0`).
- Integration (sim `m.rearTurned`, runtime `FFollowerState::bRearTurned`): only the walking (`mode walk`, not the wall layout) rear guard
  (the allocator's `rearGuard`); `wayBlocked` is evaluated only while he is not turned (it delays the start, never ends a turn). Turned: he
  faces his travel (sim: the step's direction, ClearLook exempt; runtime: no formation look -> he faces his movement) - the backward cap
  (`move.backward_mult`) no longer applies once his body has turned, he catches up at walk x `move.catchup_mult`. `Codex.Formation.RearTurn`
  0 = v2.5.1 (A/B); log `[Formation] <name> (rear guard) turns round to catch up facing forwards` / `is back - walks backwards again`;
  `IsFormationRearTurned`, `GetFormationRearTurnCount`.
- Golden `formation_RearCatchUp.json`: op `turn` {lag, turned, wayBlocked} -> {turned}; op `way` {pos, slot, others} -> {blocked}.

## 19. Saved formation shapes - the formation editor's file in the game (game designer 2026-11-10, variant B; runtime 2026-11-11)
The Training Ground formation editor (task 008: `shapesSchema.ts`, `shapesCoverage.ts`, `FormationEditor.tsx`) saves
`Content/Data/FormationLab/formation_shapes.json`, schema `codex.formation_shapes/1`. The TS simulator (`sim.ts` `getSavedFormationShape`,
`savedShapeTargets`) and the game (C++ `Source/CodexTactics/*/Formation/FormationShapesFile.*`, `FormationShapes::`) read it the same way.

### 19.1 The file
```json
{ "schema": "codex.formation_shapes/1",
  "formations": { "diamond": { "4": { "members": [ { "role": "commander", "fwd": 0, "right": 0, "look": 0, "arc": 90 },
                                                  { "role": "right", "fwd": -280, "right": 260, "look": 60 }, ... ] } } },
  "custom": { "custom_1": { "members": [ { "squad": 0, "fwd": 0, "right": 0, "look": 0 }, { "squad": 2, "fwd": -250, "right": 300, "look": 60 } ] } } }
```
- `formations.<name>.<count>`: count "2" / "3" / "4"; `members.length == count`; `members[0]` the commander at (0, 0); roles unique and equal to
  `rolesFor(count)` (2: commander + rear; 3: + right; 4: + left); `fwd` / `right` integer cm in the leader's frame (forward along the heading,
  right = heading + 90), within `CUSTOM_MAX_RADIUS` (4000); `look` integer deg relative to the heading in (-180, 180]; `arc` optional integer
  10..360 (absent = 90; `"arc": null` is an error, as in TS `m.arc !== undefined`). Unknown keys are allowed (the editor keeps them).
- `custom.custom_1..3`: `members [{squad 0..3 unique, fwd, right, look, arc?}]` (squad 0 at (0, 0); members[0] = the anchor, 17.2).
- Strict reading (C++ `FormationShapes::Parse` = TS `validateFormationShapes`): JSON numbers must be integers (no string / bool coercion); any
  error rejects the WHOLE file (the TS parse throws). The C++ also drops, with a warning and no error, a formation name the game does not know and
  `wall` / `hedgehog` / `blizzard` / `custom` (rule-driven), and a `pair` entry other than "2".

### 19.2 Which shape (C++ `FormationShapes::Find(file, formation in effect, memberCount)`)
1. `formations[<formation>][min(n, 4)]` - the formation IN EFFECT (after the guard: the mirror echelon, the trail column and the custom shape are
   their own: the trail column and the custom shape never read `formations`).
2. The pair: the game's pair is the wedge / diamond with 2 members (menu 1:30, HUD "Pair") -> `formations.pair["2"]` when the exact entry is not
   saved. No other 2-man formation (column, line, echelons) ever takes the pair (review 008 finding 4).
3. Echelons: an echelon not saved -> the other echelon's shape for that count MIRRORED (`mirrorFormationShape`: right -> -right, look -> -look
   (-180 -> 180), left <-> right, arc kept) - so a saved echelon_left also serves the guard's mirror (10.1 level 1).
4. Nothing -> the formula of `formation_config.json` (sections 2 / 12 / 13), unchanged.
Never from the file: wall, hedgehog, blizzard (rule-driven), the trail column (the wall / narrow passage / sharp-turn fold, 10.1 / 13.6 - the
guard is unchanged and still tests the formula's slots), the custom shape (17).
Known difference to the TS lookup (`getSavedFormationShape`): TS gives `pair` to a 2-man COLUMN (before a saved `column/2`) and never to the
2-man wedge - the C++ follows the review finding above; the golden cases leave `pair` out. Recommended TS fix: use `pair` for wedge / diamond
with 2 members only.

### 19.3 Slots, looks, arcs (`FormationShapes::Slots` = TS `savedShapeTargets`)
`pos = localToWorld(leaderPos, heading, [fwd, right])`, `yaw = normYaw(heading + look)`, `arc = arc ?? 90`. The runtime puts them in
`Sectors.FrameSlots` (role order) and keeps the shape's looks fixed: no coverage allocator (13.x; the TS sim skips it too), no rear guard, so no
rear catch-up turn (18.2); the corner watch on patrol (11) and ClearLook (13.1) still apply as for the formula; the places are still dealt by
minimal travel (10.6). A run and the menu's "All forward" keep facing 12 (LookYaw). The arc is carried per role
(`USquadSubsystem::GetFormationLookArc`) - the TS simulator uses it only for the editor's coverage radar, the game does not yet narrow /
sweep looks by it (open for the game designer). `IsFormationSavedShape` / `GetFormationSavedShapeName` ("diamond/4", "echelon_right/4 mirrored");
the log line `[Formation] saved shape: ... in effect` on every change.

### 19.4 The custom defaults
`custom.custom_k` = the DEFAULT of custom slot k: a slot the player stored nothing in shows it (the menu's Custom k is filled, the placement
mode starts from it); once he stores his own shape (placement, save game, campaign carry) his wins. Only his own shapes are exported
(`ExportFormationCustomSlots`, save game `formation_custom`), so a file default is never frozen into a save; clearing his slot shows the
default again. (`GetFormationCustomShape` = in force, `GetFormationCustomOwnShape` = his, `IsFormationCustomSlotDefault`.)
Why `SaveGameSubsystem.cpp` changed: its `formation_custom` writer called `GetFormationCustomShape`, which now returns the shape IN FORCE (a
file default included) - without the switch to `GetFormationCustomOwnShape` a save would freeze the designer's default as the player's own
shape, and a later edit of `formation_shapes.json` would no longer reach that slot after a load.

### 19.5 Live reload, A/B
`FormationShapes::Get()` reads the file on first use; in non-shipping builds it re-reads it when its timestamp or size changes (checked every
0.5 s), so a Training Ground save shows up without a restart; a removed file = the formula again; an invalid save keeps the last valid shapes
(warnings list the errors). `Codex.Formation.SavedShapes 0` = the file is ignored (A/B).
